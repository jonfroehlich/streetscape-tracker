# GSV throughput: why the grid run fell short of its configured rate

**Ran:** 2026-09-30, offline, on an Apple M1 Max laptop; no Google request was made ·
**Verdict:** the client was the bottleneck, and per-OK work was not the cause.
A fresh connector per batch, a barrier after every batch, and a token bucket that discarded its own sleep overrun held the engine to 56–93% of 48,000/min in the scenario that best matches production (and to 31% in the slowest).
With one session per run, 4 batches in flight and the bucket fixed, the engine sustains **48,000/min** wherever the mean response latency is under about 62 ms.
Record: [`gsv-throughput_metrics.json`](gsv-throughput_metrics.json), generated by `scripts/gsv_throughput_bench.py`.

## The question

[#304](https://github.com/jonfroehlich/streetscape-tracker/issues/304): prod paces the GSV grid run at `max_requests_per_minute = 48000` (80% of the 60,000/min Google approved for the project).
Measured from `runs` on makelab2, dense cities never got near that: 38–52% of it in the first sample (n=16) and 51–90% in a disjoint second sample (median 63%, n=19).
How far short a city fell was a clean monotone function of its coverage rate, so the issue asked whether the cost was per-`OK`-response, and named three candidate causes:
the connection limit, single-core event-loop saturation, and the systemd CPU cap.
The GSV channel is 66–76% of a night's wall clock, so this is the largest single lever on the nightly batch.

## Method

`scripts/gsv_throughput_bench.py` drives the **real** `download_gsv.collect_points_async` against a local HTTPS stand-in for the metadata endpoint.
The stand-in answers OK or ZERO_RESULTS by a hash of the location, so the coverage fraction is exact and every arm sees the same answers.
Each status gets a lognormal latency (sigma 0.5) with its own mean.
A proxy adds 1 ms to every TCP chunk in each direction (a 2 ms round trip), so a new connection pays a real connect and TLS handshake.
The client's connector is redirected to the proxy with certificate verification off, so a real handshake is **cheaper** here than against Google.
Every run is 12,000 requests at prod's `batch_size = 100`, `connection_limit = 50` and 48,000/min.
**Steady-state rate** counts server arrivals after the first 2 s, which excludes the limiter's one-second start burst.
Every arm runs 3 times per cell, interleaved; the tables quote the median and `[min–max]`.

Arms:

| arm | what it is |
|---|---|
| `baseline` | the engine at `2a94a68`, extracted with `git archive` |
| `depth1` | this change's engine with the barrier kept (connection reuse alone) |
| `depth2`, `depth4` | this change's engine with 2 or 4 batches in flight |
| `depth4-oldpacer` | `depth4` with the token bucket's pre-#304 `acquire` patched back in |

### The latency is an input, and the "fit" is a fit

Nothing offline can observe how fast Google answers, so the scenarios bracket it:

| scenario | ZERO_RESULTS mean | OK mean |
|---|---|---|
| `fit` | 15 ms | 45 ms |
| `slow-ok` | 30 ms | 60 ms |
| `slower-ok` | 30 ms | 90 ms |

**`fit` is labelled as a fit, never as a measurement.**
It is the scenario whose *baseline* curve most resembles production's: 44.6k / 33.3k / 29.0k / 26.8k at 3 / 25 / 50 / 75% coverage here, against 43.3k at 3.0%, 32.4k at 25.2%, 29.2k at 46.4% and 25.4k at 69.0% in #304's second table.
That resemblance is **not unique**: round trip, sigma and the two means trade off against each other, and prod's CPU, TLS verification and network differ from this laptop's.
It says Google's latencies are plausibly in this range; it does not say they are these numbers.

## Results

### Client CPU per OK row is negligible

With no latency and pacing off (the `cpu-ceiling` cell), the baseline engine ran **105k/min** at **0.35 ms of CPU per request**, opening **6,000 connections for 12,000 requests**.
The new engine ran **535k/min** at **0.11 ms**, on **50** connections.
That 0.11 ms covers everything a request costs the client, row building included, so per-OK work cannot be what cost half the rate.
Nor does the OK share move it: at `fit`, depth 4 spends 0.364 / 0.355 / 0.355 / 0.354 ms per request at 3 / 25 / 50 / 75% coverage.
Every paced cell used 0.15–0.31 of a core (median CPU per request × median rate), so **neither cause 2 (event-loop saturation) nor cause 3 (the 4-core systemd cap) binds**.

**Why the loss tracks coverage.**
The baseline curve falls with coverage in every scenario, and only when OK is the slower class.
That comes from the barrier, not from client-side work: each batch lasts as long as its slowest connection, so every OK in a batch lengthens it.
`depth1` (connection reuse without pipelining) recovers 9–24% and keeps the same monotone shape.
Removing the barrier is what flattens it.

**The token bucket was the next ceiling.**
With the barrier gone, the limiter binds, and the old bucket then delivered **37.9–40.0k** where it bound (79–83%).
It slept `(1 − tokens) / rate` and then set `tokens = 0`, throwing away every sleep's overrun.
The fixed bucket refills from the clock after the sleep and delivers 47,995–48,041 in every cell where it binds.

**Readings above 48,000 are bursts, not a broken ceiling.**
A connection-limited stretch lets the bucket refill toward its one-second capacity (800 tokens), and the next stretch spends it.
Over a 13 s window, 800 tokens are worth up to +3.7k/min.
Over any interval T the bucket admits at most 800 + 800 × T requests, and `test_rate_limiter_crediting_the_overrun_never_exceeds_the_rate` pins exactly that.
The baseline burst the same way after every barrier.

**Depth 4, not 2.**
Both reach the ceiling at `fit` and at every scenario's 3% coverage.
Where OK responses are slow, depth 2 falls short: `slower-ok` at 25 / 50 / 75% gives 42.0k / 35.6k / 31.5k for depth 2 and 49.6k / 46.0k / 37.9k for depth 4.
Depth 4 costs nothing measurable: median peak RSS was 203–212 MB in every arm of the new engine (the baseline's was 278–323 MB), and at most 400 request coroutines are in flight.

**Where 50 sockets bind.**
`slower-ok` at 75% coverage stays at about 38k whatever the depth or pacer.
That is Little's law: 50 sockets over a mean latency of about 77 ms is about 39k/min.
So the fixed engine reaches 48k exactly when Google's mean latency is under about 62 ms (50 / 800 per second).
If it is higher, the next lever is `connection_limit`, and that is a pacing decision, not a tuning one.

## What changed

- `download_gsv.collect_points_async`: one `ClientSession` for the whole run, and `PIPELINE_DEPTH = 4` batches in flight.
  Batches are still written in submission order by the unchanged row builder, so the CSV is byte-identical.
  `tests/fixtures/gsv_golden_run.csv` was generated by the sequential engine and pins that, with out-of-order completion, a retry pass and a residual failure row.
- `AsyncRateLimiter`'s token-bucket path credits the sleep overrun.
  Only non-jittered callers use that path: `download_gsv` (gsv, gsv_streets), `download_kartaview` (where a 3.75 s gap makes the overrun negligible), and Mapillary or Panoramax only if jitter is explicitly set to 0.

## Caveats

- One laptop, one simulated round trip (2 ms), a lognormal latency model, and certificate verification off.
  Prod's absolute CPU figures will be higher, but the per-OK share stays small.
- The expected prod gain is conditional on Google's latency, which nothing here measured.
  Under `fit` it is 1.08× at 3% coverage, 1.44× at 25%, 1.65× at 50% and 1.79× at 75%, against #304's 63% prod median, roughly 1.6×.
- **Measure it in production after deploy**: `api_requests / (duration_seconds / 60)` from `runs` for the same high-coverage cities, before and after, as #304 did.
  Two follow-ups wait on that number: re-deriving `scheduler._ACHIEVED_RATE_FRACTION` (0.5 today; over-timing is the harmless direction, so it stays until then), and the 10M daily budget, which is already 99.9% spent every night, so a faster engine finishes it sooner rather than collecting more cities.

