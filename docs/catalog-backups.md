## Catalog backups (`catalog_backup.py`, issue #145)

**Catalog backups (`catalog_backup.py`, issue #145).** The catalog is the operational source of truth and is never rsynced, so it lives in exactly one place — and UW CSE IT confirmed on 2026-08-05 that `/projects/makeabilitylab` on makelab2 **was not being snapshotted or backed up at all** until that day (the second such misconfiguration in two months; treat "it's on lab storage" as not implying "it's backed up"). Two facts survive their fix: a ZFS snapshot of a **live** WAL-mode SQLite file may be torn, and a backup nobody observes is indistinguishable from no backup — which is exactly how #145 happened. So: dated `backups/streetscape_tracker.db.{DATE}.backup` copies via SQLite's **online backup API** (`conn.backup()`, transactionally consistent against a live WAL DB — no `VACUUM INTO` needed, which is CSE IT's "keep a periodic dumped copy in the same directory" recommendation satisfied), written to a `.tmp` sibling, verified with `PRAGMA integrity_check`, and only then `os.replace()`d — so a snapshot can't catch a half-written file and a bad copy can't overwrite a good one. Retained `KEEP_DAYS = 14` (matching the website's `pg_dump` retention, makeabilitylabwebsite#1444) except the **newest is never pruned regardless of age**, or a backup failing longer than the window would end with pruning deleting the last good copy. `run-due` backs up **twice**: before the city loop (the tail runs after any loop-level failure but **not** a SIGKILL — the #157 OOM mode — so a tail-only backup is missing on exactly the bad nights; also covers zero-due nights) and again in the tail (so the retained copy reflects the runs the night registered). A failure alerts **unconditionally**, ignoring `[alerts].failure_threshold`, and exits nonzero, but never withholds publishing (#167's posture). `backup_status.json` records every attempt **including failures** — outcome, source DB, host, per-table row counts, counted on the **copy** rather than the live catalog since the point is to describe the file an operator is holding. Two hazards that the mechanism has to handle rather than document. (1) **Sidecars must never outlive their database file.** Nothing binds a `-wal` to a particular DB — SQLite replays whatever valid frames sit beside the main file — and since the online backup API copies the source's file-format version, every dated copy is itself WAL-format, so *any* read of one (including a read-only one, which can't clean up after itself) strands a pair. They are cleared at promotion and prune time, and `restore_backup` **refuses** when it finds them beside the destination instead of deleting them: that is exactly the shape of a real incident (catalog goes bad → operator moves the DB aside → the dead process's sidecars remain), where replaying them hands back the state the restore was escaping with `integrity_check` still reporting "ok" — and an orphaned WAL may equally be the only copy of the last committed writes, so it is the operator's call. (2) **The copy is bounded**: `sqlite3`'s backup API retries `SQLITE_BUSY` forever (`busy_timeout` doesn't apply), and the pre-flight call sits in front of the whole city loop, so a stuck copy costs the night and ends in a SIGKILL — a progress-callback deadline (`BACKUP_TIMEOUT_S`) supplies the timeout sqlite3 lacks, and an open transaction on the source connection is rejected outright. `scheduler backup-status` reports health plus an inventory of the assets published **nowhere** and thus single-copy: `archive/gsv_driving_plan/` (Google overwrites the feed in place, so a lost snapshot is permanently gone) and `data/osm_cache/` (refetching yields different edge IDs and sample points, breaking #101 walk-diff continuity rather than merely costing a download). It exits nonzero when the newest copy is missing, **older than `STALE_AFTER_HOURS` (48 h)**, or the last attempt failed — the age gate is not redundant with the outcome, since "the last attempt succeeded" stays true forever once the scheduler stops running at all, and the newest file is deliberately never pruned. **That exit code needs a caller other than the scheduler** (issue #193): the only thing that would have run it was the process whose absence the age gate detects, so a separate daily user timer (`deploy/systemd/streetscape-backup-check.{service,timer}`, noon Pacific, same `ConditionHost` pin — a cutover must flip both) runs `backup-status --alert`, which emails the report through `[alerts]` when unhealthy, stays silent when healthy, names the verdict in the subject, and leaves the exit status alone. Deliberately not the `OnFailure=` notify unit: it isn't installed on makelab2 and mails the scheduler log tail rather than the report. `scheduler restore-backup PATH [--to DEST]` is the incident-time handle for `restore_backup`, drilled end-to-end in the tests.

## The staging path is per-writer, not per-date (issue #214)

**Written after the split — a correction to the paragraph above, which describes the original
per-date staging file.** Once the operator catch-up became a supported path, "the nightly timer
fires while a manual run is still going" became an ordinary event rather than a mistake, and the
catalog backup was the one part of the night that did not tolerate it: two overlapping runs staged
the same path, one unlinked the other's in-progress copy, and `verify → os.replace` then promoted a
torn file as the day's verified backup with a clean `"ok"` in `backup_status.json` beside it.
`catalog_backup._staging_path` therefore names the **writing process** (host + pid), for both the
copy and the status file, and abandoned staging files are swept by *age* (`_STALE_TMP_AFTER_S`,
above any live copy's `BACKUP_TIMEOUT_S`) rather than by name. So the `.tmp` sibling named above is
the shape of the defect, not the current design. The concurrency context it came from is in
[`provider-access.md`](provider-access.md), under "Two `run-due` processes can overlap".
